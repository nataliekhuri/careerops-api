# Security review (M6)

Reviewed 14 November 2026, ahead of a public launch. Everything below is **implemented
and tested locally**; nothing here has been deployed (see
[FEATURES.md](FEATURES.md) for what is actually live).

## 1. Authentication

| Area | Status | Detail |
|---|---|---|
| Password hashing | ✅ | Argon2id via `pwdlib`, recommended parameters (`app/core/security.py`). |
| Login timing | ✅ | An unknown email still runs a password hash (`_DUMMY_HASH`), so response time does not reveal which emails are registered. |
| Tokens | ✅ | JWT (HS256), requires `exp`, `iat`, `sub`, `type`; a 32+ character secret is required at startup or the API refuses to start. Tested against garbage tokens, wrong secret, expired, wrong `type`, `alg: none`, and missing claims. |
| Password strength | ✅ | 8–128 characters, must mix letters with numbers/symbols (not pure digits or pure letters). |
| Account deletion / password change | ✅ | Both re-check the current password; deletion cascades to all of the user's data (tested). |
| **Login brute-force** | ✅ **new in M6** | `app/api/rate_limit.py`: 5 attempts per email + 20 per IP, both per 15 minutes, on `/auth/login`. Both successful and failed attempts count, so repeated valid logins from a script are also capped. 429 with `Retry-After`. |
| **Registration abuse** | ✅ **new in M6** | 5 registrations per IP per hour on `/auth/register`. |
| CAPTCHA / distributed abuse | ❌ not implemented | The in-memory limiter is per-IP; a distributed script using many IPs is not slowed down. Adding a CAPTCHA (e.g. hCaptcha/Turnstile) needs a third-party key and is a cost/dependency decision — **not added without approval**. |
| Login rate limit scope | ⚠️ known limit | The limiter is in-process, correct only because Render's free plan runs a single instance (documented in `app/core/rate_limit.py`). Scaling to multiple instances would need a shared store (e.g. Redis); the call sites would not change. |

## 2. Authorization / data isolation

Unchanged from M1–M5, re-verified this review:

- Every query is scoped to `user_id`. Another user's record (application, company,
  interview, AI endpoints by `application_id`) answers **404** (or **422 "not found"**
  for a reference), identical to a non-existent id — tested for every resource,
  including the M5 AI endpoints.
- The database itself enforces that an interview's owner matches its application's
  owner (composite foreign key), so a bug in the API could not cross users even if the
  `user_id` filter were accidentally dropped.
- `career_profiles.user_id` is the primary key: one profile per user, deleted by the
  same `ON DELETE CASCADE` as applications/companies/interviews.

## 3. Transport and response headers

| Header | Where | Value |
|---|---|---|
| `Strict-Transport-Security` | API, **new in M6** | Sent once a request reaches the API over HTTPS (`app/core/security_headers.py`); never sent over plain HTTP, so it cannot break local development. |
| `X-Content-Type-Options` | API, new | `nosniff` |
| `X-Frame-Options` | API, new | `DENY` |
| `Referrer-Policy` | API, new | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | API, new | Denies camera, microphone, geolocation, payment |
| `Content-Security-Policy` | Frontend only, new | Set at the Render static-site level (`render.yaml`), not on the API. The API is a JSON endpoint whose own `/docs` and `/redoc` load CDN scripts, so a strict CSP there would either break the docs or need a looser, less useful policy; the frontend — the thing actually rendering HTML in a browser — gets the strict policy instead. |
| CORS | Unchanged, re-verified | `allow_credentials=False` (tokens are sent as `Authorization: Bearer`, never cookies, so no credentialed CORS is needed); **fails closed**: if `CORS_ORIGINS` is unset, no cross-origin browser calls are allowed at all, by any origin. Production sets it to exactly the frontend's URL (`render.yaml`). |

All header tests: `tests/test_security_headers.py`.

## 4. Error handling

Unchanged from M1, re-verified:

- Unhandled exceptions → generic `500 {"detail": "Internal server error"}`; the real
  exception (with traceback) is only in the server log.
- A database outage → `503 {"detail": "Service temporarily unavailable"}`; connection
  errors (which can contain hostnames) are never put in the response.
- Validation errors → `422` with the specific field and message (safe to show: it only
  describes the request the caller just sent, nothing about other data).
- Tested: `tests/test_reliability.py`.

## 5. Production configuration

| Setting | Status |
|---|---|
| `JWT_SECRET_KEY` | Required, ≥32 chars, generated by Render (`generateValue: true`), never in Git. |
| `DATABASE_URL` | Generated by Render from the managed database; never in Git. |
| `CORS_ORIGINS` | **New in M6**: set in `render.yaml` to the exact frontend origin. |
| `RUN_MIGRATIONS=true` | Runs `alembic upgrade head` at container start (free plan has no pre-deploy hook); a failed migration fails the deploy and leaves the previous version serving. |
| `FORWARDED_ALLOW_IPS=*` | Trusts Render's proxy for `X-Forwarded-*` (Render terminates TLS and proxies internally; `*` is standard for a PaaS where the only inbound path is that proxy). This is also what makes `request.url.scheme` and the rate limiter's `client_ip()` correct in production. |
| Non-root container | `Dockerfile` runs as `appuser` (uid 10001), not root. |
| Database network | `ipAllowList: []` — unreachable from the public internet, only from Render's private network. |
| AI provider | `AI_PROVIDER` only accepts `"builtin"` (rejected otherwise) — no paid/external AI service can be switched on by configuration (`app/ai/providers.py`). |
| Request size limits | Job descriptions ≤20,000 chars, CVs ≤30,000 chars, notes ≤5,000 chars, etc. — enforced by Pydantic, tested. |
| `/docs`, `/redoc` | Left public (no secrets in the schema); a conscious choice for a portfolio project, not an oversight. |

## 6. Frontend

- No secrets in frontend code or build output; `VITE_API_URL` is the only
  environment-specific value, and it is a public URL, not a secret.
- The static site build is served with security headers and a strict CSP (section 3).
- `localStorage` holds only the bearer token (no password, no PII beyond what the
  token's claims already are: a user id and expiry).

## Summary of what changed in M6

1. Login/registration rate limiting (`app/core/rate_limit.py`, `app/api/rate_limit.py`).
2. API security response headers (`app/core/security_headers.py`).
3. Frontend security headers and CSP (`render.yaml`, `careerops-web` service).
4. `CORS_ORIGINS` set to the real frontend origin in production config.
5. Privacy notice page (`frontend/src/pages/Privacy.tsx`).

Nothing in sections 1–6 required changing the existing auth, isolation or error-handling
design from M1–M5 — that review found no issues worth changing.
